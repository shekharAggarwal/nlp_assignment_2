  • Task: BERT variant comparison (general-domain BERT vs domain-specific BERT)
  • Dataset: PubMedQA, pqa_labeled subset (1000 expert-labelled questions)
  • Models: bert-base-uncased and microsoft/BiomedNLP-PubMedBERT-base-uncased-abstract
  • Metrics: Accuracy, Precision, Recall, F1

PubMedQA gives a research question (usually taken from the title of a PubMed paper) and the abstract of that paper without its conclusion. The model has to answer yes / no / maybe. We treat it as 3-class sequence-pair classification: the question is segment A and the abstract text is segment B.

Both models are BERT-base with the same architecture (12 layers, 768 hidden, 110M params). The difference is the pretraining data and vocabulary. BERT was trained on Wikipedia + BookCorpus, while PubMedBERT was trained from scratch on PubMed abstracts and has its own WordPiece vocab built from that text. So any gap between them comes from the domain of pretraining, which is what this assignment wants us to look at.

2. Dataset loading¶

The pubmed_qa dataset on the Hugging Face Hub has moved to qiaojin/PubMedQA (the old name was a script-based loader; with the datasets version we used, load_dataset("pubmed_qa", ...) fails because repo ids now need a namespace). The data is the same. It has three configs:

  • pqa_labeled: 1k questions labelled by experts (yes/no/maybe)
  • pqa_unlabeled: 61k without labels
  • pqa_artificial: 211k labelled automatically by a heuristic (yes/no only)

We use pqa_labeled because it is the only one with human labels and the "maybe" class.

The labels are imbalanced: about 55% yes, 34% no and only 11% maybe. A model that always says "yes" already gets ~0.55 accuracy, so accuracy alone can be misleading here. We report macro-F1 as the main metric and also keep a majority-class baseline in the results table.

Important: each row also has a long_answer field, which is the conclusion of the abstract. It basically states the answer ("...these results suggest that X does not ..."), so using it as input would leak the label. We only use question + context.contexts. This matches the "reasoning-required" setting from the PubMedQA paper.

3. Preprocessing and tokenization¶

Steps:

  1. Join the abstract sections into one passage (the section titles like BACKGROUND/RESULTS are dropped).
  2. Map labels to ids.
  3. Make a stratified 70 / 10 / 20 split (train / validation / test). The split is made once with a fixed seed, and both models use exactly the same split.
  4. Tokenize as a sentence pair [CLS] question [SEP] context [SEP]. If the pair is longer than 512 tokens, only the context gets truncated (truncation="only_second"), so the question is never cut.

All inputs are padded to 512 inside the data collator. We first tried dynamic padding (pad to the longest example in the batch), but on Apple MPS the changing tensor shapes made memory use grow until the laptop started swapping and each step took ~30 s instead of ~2 s. Fixed-size batches fixed it.

4. Model loading and fine-tuning¶

Both models are loaded with AutoModelForSequenceClassification. This puts a new linear layer (768 -> 3) on top of the [CLS] output; the layer starts random and is trained with the rest of the model.

Training details (identical for both models):

  • AdamW, lr 3e-5, linear decay with 10% warmup, weight decay 0.01, effective batch size 16 (8 x 2 accumulation steps)
  • 10 epochs, evaluate on validation after every epoch, and keep the checkpoint with the best validation macro-F1 (not lowest loss / best accuracy, because those can favour the "always yes" behaviour). We don't use early stopping: the validation set has only 100 examples, so its F1 jumps around between epochs and early stopping could end a run too soon.
  • class-weighted cross-entropy: weights are inversely proportional to class frequency in the training set, so that mistakes on the small "maybe" class (11%) cost more.
  • 3 random seeds per model. The training set is small (700 examples), so results change a fair bit from seed to seed, and one run could give a misleading comparison.

class WeightedTrainer(Trainer):
    """Trainer with class-weighted cross entropy."""

    def __init__(self, *args, **kwargs):
        super().__init__(*args, **kwargs)
        # our loss is a plain mean over the batch, so the Trainer has to divide it by the number of
        # gradient accumulation steps itself. Without this flag it assumes the model already did that
        # (BertForSequenceClassification.forward takes **kwargs) and the logged loss comes out 2x too big.
        self.model_accepts_loss_kwargs = False

    def compute_loss(self, model, inputs, return_outputs=False, num_items_in_batch=None):
        labels = inputs.pop("labels")
        outputs = model(**inputs)
        loss_fn = torch.nn.CrossEntropyLoss(weight=class_weights.to(outputs.logits.device))
        loss = loss_fn(outputs.logits, labels)
        return (loss, outputs) if return_outputs else loss


def compute_metrics(eval_pred):
    logits, y_true = eval_pred
    y_pred = logits.argmax(-1)
    p_m, r_m, f_m, _ = precision_recall_fscore_support(y_true, y_pred, average="macro", zero_division=0)
    p_w, r_w, f_w, _ = precision_recall_fscore_support(y_true, y_pred, average="weighted", zero_division=0)
    return {
        "accuracy": accuracy_score(y_true, y_pred),
        "precision_macro": p_m, "recall_macro": r_m, "f1_macro": f_m,
        "precision_weighted": p_w, "recall_weighted": r_w, "f1_weighted": f_w,
    }

def train_one(model_name, seed):
    path = MODELS[model_name]
    tok = tokenizers[model_name]
    ds = encoded[model_name]
    run_dir = f"{OUT_DIR}/ckpt_{model_name}_{seed}"

    set_seed(seed)
    model = AutoModelForSequenceClassification.from_pretrained(
        path, num_labels=len(LABELS), id2label=id2label, label2id=label2id)

    args = TrainingArguments(
        output_dir=run_dir,
        eval_strategy="epoch",
        save_strategy="epoch",
        save_total_limit=1,
        load_best_model_at_end=True,
        metric_for_best_model="f1_macro",
        greater_is_better=True,
        logging_strategy="epoch",
        report_to="none",
        seed=seed,
        **HPARAMS,
    )
    trainer = WeightedTrainer(
        model=model,
        args=args,
        train_dataset=ds["train"],
        eval_dataset=ds["validation"],
        data_collator=DataCollatorWithPadding(tok, padding="max_length", max_length=MAX_LEN),
        compute_metrics=compute_metrics,
    )

    start = time.time()
    trainer.train()
    minutes = (time.time() - start) / 60

    # per-epoch validation curve, for plotting later (taken before the extra evaluate() call below)
    history = [h for h in trainer.state.log_history if "eval_f1_macro" in h]

    val = trainer.evaluate(ds["validation"])   # this is the best checkpoint, reloaded at the end of training
    test_out = trainer.predict(ds["test"])
    probs = torch.softmax(torch.tensor(test_out.predictions), -1).numpy()

    return trainer, {
        "model": model_name,
        "seed": seed,
        "best_epoch": min(history, key=lambda h: -h["eval_f1_macro"])["epoch"],
        "epochs_run": history[-1]["epoch"],
        "minutes": round(minutes, 1),
        "val_f1_macro": val["eval_f1_macro"],
        **{k.replace("test_", ""): v for k, v in test_out.metrics.items() if k.startswith("test_")
           and not k.endswith(("runtime", "per_second", "loss"))},
    }, probs, history

Training loop. For every run, the test-set probabilities are saved so the later analysis can use them without retraining. For each model we also keep the run with the best validation macro-F1 (the test set is not used to pick it) and save it to outputs/best_<model> for the custom-example predictions. Results, histories and probabilities are written to outputs/ after every run. If the notebook is re-run, finished runs are loaded from disk instead of being trained again (training all 6 runs takes over an hour on our laptop).

for model_name in MODELS:
    for seed in SEEDS:
        if (model_name, seed) in done:

7.6 Summary of the error analysis¶

  1. Most errors are mix-ups between yes and no. For PubMedBERT the most common error is yes -> no (27). For BERT it is no -> yes (34), so BERT tends to say "yes" when it is unsure, and PubMedBERT handles "no" much better. Out of 200 test questions, 50 are answered correctly only by PubMedBERT and 26 only by BERT, so BERT is not just a weaker copy of PubMedBERT; they make different mistakes.
  2. "maybe" is almost never predicted correctly (BERT 5/22, PubMedBERT 1/22). Most true "maybe" questions are predicted as "yes". In several of them the abstract does report a significant result (e.g. the VEGF example), and the "maybe" comes from the authors' cautious wording in the conclusion. The conclusion is in long_answer, which the model never sees, so some of these are very hard to get from the input alone.
  3. Input length and truncation don't seem to matter much. Accuracy does not drop for longer abstracts, and only 10 (BERT) / 4 (PubMedBERT) test examples were truncated at all, which is too few to say anything about truncation.
  4. Both models are overconfident. The average confidence on wrong answers is close to the average on right ones (PubMedBERT 0.75 vs 0.81, BERT 0.70 vs 0.73), and PubMedBERT gives probabilities near 1.00 on some wrong answers. So the probability is not a good signal of when the model is wrong.
  5. PubMedBERT's advantage is a bit larger on the most fragmented third of the test set (gap 0.149 vs about 0.105 for the other two thirds). That fits the idea that the domain vocabulary helps with technical text, but with about 67 examples per group the difference is small and could easily be noise. We would not call it proven.
  6. A lot of the questions both models get wrong need some reasoning over numbers. For example, in "Are adult body circumferences associated with height?" (gold: yes) the abstract reports small but significant increases per cm of height. In the hot-flash device example (gold: no), the key fact is a 24% concordance rate, and the model has to know that this is low. A classifier on top of the [CLS] token doesn't do this kind of reasoning well, especially with 700 training examples.

8. Conclusion¶

  • PubMedBERT did better than BERT on all four metrics. With the 3-seed ensemble the gap is 0.670 vs 0.550 accuracy and 0.498 vs 0.454 macro-F1.
  • Both models have the same architecture, size and fine-tuning setup, so the difference comes from pretraining. PubMedBERT was pretrained on the same kind of text as this task (PubMed abstracts), and its vocabulary fits that text better (1.37 vs 1.53 tokens per word, so many biomedical terms are single tokens instead of several pieces).
  • The gain is not uniform. It comes from the "yes" and "no" classes. "maybe" stays very poor for both models, and there BERT is actually a bit better. Results also vary a lot between seeds, and on one of the three seeds BERT was slightly ahead. This matches what Gu et al. (2020) report for PubMedQA.
  • The task is hard for both models: the best macro-F1 is below 0.5. The main reason is the small amount of labelled data (700 training questions), together with the fact that "maybe" often depends on the authors' conclusion, which is not part of the input.

Limitations / what we would try next

  • Only 3 seeds and one data split. With 200 test examples, one question is worth 0.5% accuracy, so 5-10 seeds or cross-validation would give more reliable numbers.
  • The 100-example validation set is noisy. The BERT run it selected (seed 42) turned out to be the weakest on the test set.
  • Hyperparameters were not tuned separately per model; both used the same standard values.
  • An extra fine-tuning step on the large automatically labelled pqa_artificial set (211k questions) before pqa_labeled would probably help with the small-data problem, but it needs more compute than we had on a laptop.
